---
title: 编写 Bun Module
description: 使用脚手架创建强类型 Bun Module，并通过正式 Execution Adapter 开发运行。
---

Bun 是官方 Module 执行路径。Bun Module 实现生成的 Capability Provider
Interface；它不实现第二套 Runtime Graph，也不自行实现 Adapter Wire。Rust Host
通过 `lenso.bun-process@1` Execution Adapter 持有进程启动、握手、有界
JSON-RPC、Deadline、取消、关闭与宿主失败转换。

## 前置条件

- Bun 1.2.21 或更高版本
- 从 npm 或 crates.io 安装公开发布的 Lenso CLI

```sh
npm install -g @lenso/cli
# 或：cargo install lenso-cli --locked
lenso --version
bun --version
```

npm CLI 内含对应平台的可执行文件并带有 Provenance。`@lenso/bun-module`
负责 Module Serving；`@lenso/bun` 发布 Bun Module 可直接引用的 Lenso 官方
Capability 投影。

## 创建完整 Bun 项目

一条命令生成 Capability Contract、TypeScript Binding、类型化 Provider、
App Composition 与 Bun Workspace：

```sh
lenso module create greeting --runtime bun
cd greeting
lenso module dev
```

默认情况下，创建过程会先在暂存目录生成完整项目，执行 `bun install` 与
TypeScript 检查，全部成功后再原子发布新目录；已有目标不会被覆盖。离线创建可用
`--no-install`，指定目录可用 `--dir PATH`，指定 Capability Identity 可用
`--capability example.greeting@1`。

生成的项目是自包含的：

```text
greeting/
├── contracts/greeting/
│   ├── capability.json
│   ├── generated/
│   │   └── bindings.ts
│   └── schemas/
├── modules/greeting/
│   ├── package.json
│   └── src/index.ts
├── bun.lock
├── lenso.json
├── package.json
└── tsconfig.json
```

`lenso.json` 会选择 Workspace Package、脚本 Entrypoint、
`lenso.bun-process@1` Execution Class 与准确的生成 Endpoint。普通
`bun.lock` 继续持有 Package Resolution 权威。

## 实现生成的 Provider

脚手架从一个类型化 Request Provider 开始：

```ts title="modules/greeting/src/index.ts"
import { defineModule, serve } from "@lenso/bun-module";
import {
  bindProvider,
  type Provider,
} from "../../../contracts/greeting/generated/bindings.ts";

const provider: Provider = {
  async execute(_context, request) {
    if (request.input.trim().length === 0) {
      return {
        ok: false,
        error: { kind: "domain", error: "invalid_input" },
      };
    }

    return {
      ok: true,
      value: { output: `Hello from Bun, ${request.input}!` },
    };
  },
};

serve(defineModule({ providers: [bindProvider(provider)] }));
```

生成的 Binding 持有 Request、Response、Domain Error、Context 与 Provider
类型。`@lenso/bun-module` 持有 Module 侧握手和 Server；业务代码不应解析
`--lenso-*` 参数、JSON-RPC Envelope、Session 或进程信号。

预期内的业务结果应返回生成的 Domain Error。抛出的异常仍属于运行时失败，并在
Adapter 边界被如实映射。

## 使用 Fresh Plan 开发

在项目根目录启动开发循环：

```sh
lenso module dev
# 等价的 Workspace Script
bun run dev
```

该命令会检查 Contract 与 Package Lock，解析一份新的不可变 App Plan，再启动
正式 JSON-RPC Bun Adapter。相关源码、Descriptor、Schema、Manifest、Lockfile
或 `lenso.json` 变化时，当前 Child Process 会被干净停止，项目重新解析后启动
Fresh Generation。类型、Contract 或启动失败不会退出 Watcher，修复后的下一次
编辑仍可恢复运行。Ctrl-C 会执行协作式关闭。

只有需要覆盖默认值时才指定 Bun 或项目文件：

```sh
lenso module dev --bun-bin /opt/bun/bin/bun
lenso module dev --project path/to/lenso.json
```

## 检查与解析

脚手架已经提供可重复执行的 CI 命令：

```sh
bun run typecheck
bun run check
bun run resolve
lenso module verify
```

`check` 校验 Descriptor、已提交的生成 Binding、Package Lock、Entrypoint、
Endpoint 与 Execution Class。`resolve` 写出规范化 Plan；运行中的 Kernel 不会
安装 Package、发现 Provider 或修改该 Graph。

## 当前交互支持

`@lenso/bun-module` 0.1 通过正式 JSON-RPC Loopback Wire 支持类型化 Request
Provider。遇到 Stream 或 Event Descriptor 时会在启动阶段拒绝，不会暴露残缺的
Authoring Contract。底层 Bun Adapter 已有跨运行时 Stream / Event Conformance，
但它们还不是公开的高层 Bun Module Authoring Surface。

Module API 见
[`@lenso/bun-module` Package](https://www.npmjs.com/package/@lenso/bun-module)，
Execution Adapter 与真实跨运行时证据见
[`lenso-bun-adapter`](https://github.com/LioRael/lenso-bun-adapter)。
