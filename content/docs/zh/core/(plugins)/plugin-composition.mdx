---
title: 向 App 添加 Plugin
description: 通过可见 Plugin Root 与 Host Catalog 组合一个 App。
---

受审查的 Authoring Authority 是可见 `plugins/` 目录。匹配的 Host Build 发布
`.lenso/host-catalog.json`；解析器合并 Host Default 与 Plugin Root 差异，生成完整、
不可变的 App Plan。

第 2 节的 built-root 命令需要可执行 Host Build，以及从这个确定 Build
生成的 `host-catalog.json`。它们定义产品实际支持的 linked Plugin、Slot、
Execution Adapter 与默认值；通用 CLI 无法自行发明这些信息。第 3 节的
源码 App 命令则从已采用的输入构建新的 Host。

## 1. 理解 App 文件

```text
my-app/
├── .lenso/
│   ├── host
│   └── host-catalog.json
└── plugins/
    └── example.echo/
        ├── plugin.lenso-plugin/
        ├── default.toml
        ├── default/
        │   └── prompt.md
        └── old.disabled
```

- `plugin.lenso-plugin/` 是验证后解出的 Bundle；
- `<instance>.toml` 添加或配置 Keyed Instance；
- `<instance>/` 保存该配置 Instance 的不可变 Resource；
- `<instance>.disabled` 是禁用已有 Instance 的空 Marker。

## 2. 通过 CLI 修改 App

使用 CLI 保持这些不变量：

```sh
lenso app init --host ./host --host-catalog ./host-catalog.json --root ./my-app
lenso plugins add ./example.echo/dist/example.echo-0.1.0.lenso-plugin --root ./my-app
lenso plugins configure example.echo default --file ./echo.toml --root ./my-app
lenso plugins disable example.echo default --root ./my-app
lenso plugins enable example.echo default --root ./my-app
lenso plugins remove example.echo default --root ./my-app
lenso plugins remove example.echo --root ./my-app
lenso app check --root ./my-app
lenso app show --root ./my-app
```

每次修改都会先使用 Host Catalog 解析 Candidate Snapshot。无效配置、缺少 Required
Slot、未知 Plugin 与歧义 Binding 会在文件提交前失败。运行中的产品 Host 另行暂存
Generation、通过 Ready Gate、切换 Route、Drain 旧 Generation，并可在运行失败时回滚。

向 `remove` 传入 Instance key 只会删除该 App-owned 差异；省略 key 会通过可恢复的
`.lenso/trash/` 路径移除整个 Plugin 目录。

`plugins list` 显示每个 Derived Plugin Instance 及其来源。`app show` 解释包含 Host
Default 与 Capability Binding 在内的完整 Derived App。人工审查或合并后，
`app check` 是最短的验证。

## 3. 按分发方式选择准确的 Release 路径

较早发布的 Portable Bundle 工作流使用下面的 `lenso plugins` 命令。它们需要
真实可下载的 Bundle 和兼容 Host；**不能**把 linked Rust `.crate` 采用到源码
App 中：

```sh
lenso plugins search tool
lenso plugins install example.tool --version 1.2.0
lenso plugins update example.tool --version 1.3.0
lenso plugins history example.tool
lenso plugins rollback example.tool --version 1.2.0
```

不存在隐式“latest”。Catalog 与 Bundle Schema 是严格的；网络下载绑定 Digest；保留
版本保持不可变。在真正存在可下载 Bundle 前，官方 Catalog 可以如实为空。
上面的 `example.tool` 坐标仅用于说明，不代表已有对应的公开发布。

下列准确签名路径需要先按[创建本地 Web App](/docs/zh/core/app-quickstart)
构建源码 CLI，并将 `LENSO_CLI` 设为该二进制的绝对路径。此候选 CLI 支持
将一个准确签名的 Portable Release 采用为源码 App 输入。签名快照、公开信任配置
和匹配的 `.lenso-plugin` 必须独立提供；Site
列表本身不授予安装权限：

```sh
"$LENSO_CLI" plugins signed-search \
  --snapshot /absolute/path/to/signed-portable.json \
  --trust /absolute/path/to/public-trust.json --json
"$LENSO_CLI" app add "$PLUGIN_ID@$VERSION" --root . \
  --portable-snapshot /absolute/path/to/signed-portable.json \
  --trust /absolute/path/to/public-trust.json \
  --archive /absolute/path/to/exact-release.lenso-plugin
"$LENSO_CLI" app build --out dist-portable-review
"$LENSO_CLI" app check --root dist-portable-review/intent
"$LENSO_CLI" app show --root dist-portable-review/intent --json
```

`app add` 在记录源码 App 意图前检查签名原文、有效期、准确 Release
身份、归档摘要与 Manifest。后续构建按本地锁检查归档是否漂移；它不能对 App
所有者可编辑的源码树建立新的独立签名权威。运行不受信任 Bundle 前，仍需审查
Host 目标与权限，并使用适当隔离。这里的坐标仅为占位符，不表示 CLI 或
Portable Release 已公开发布。

同一 CLI 还提供另一条准确签名的 linked Cargo 路径。在源码 App 中，
先用本地公开信任配置检查运营方提供的签名快照。取得准确匹配的 Registry
`.crate` 归档，并审查 Host 目标和集成方式后，命令形状如下：

```sh
"$LENSO_CLI" app linked-catalog \
  --linked-snapshot /absolute/path/to/signed-linked.json \
  --trust /absolute/path/to/public-trust.json --json
"$LENSO_CLI" app add "$PLUGIN_ID@$VERSION" --root . \
  --linked-snapshot /absolute/path/to/signed-linked.json \
  --trust /absolute/path/to/public-trust.json \
  --crate /absolute/path/to/exact-package.crate
"$LENSO_CLI" app build --out dist-linked-review
"$LENSO_CLI" app check --root dist-linked-review
"$LENSO_CLI" app show --root dist-linked-review --json
```

上面的 `PLUGIN_ID`、`VERSION` 和文件路径都是占位符，不代表已有公开发布。
`app add` 会在采用源码前检查签名、准确身份/版本、Crate 摘要及 Native Host
目标。本站未签名的候选文档不能作为这些输入。仅有签名列表、缺少 `.crate` 或
信任材料仍不算安装成功；采用成功之后还需构建、检查并真实调用 App。

Kernel 从不读取该目录，也不安装 Package；它只接收某个 App Generation 选择的
Resolved Plan。
