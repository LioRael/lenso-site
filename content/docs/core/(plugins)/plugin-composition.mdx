---
title: Add Plugins to an App
description: Compose one App through its visible Plugin Root and Host Catalog.
---

The reviewed authoring authority is a visible `plugins/` directory. The matching
Host Build publishes `.lenso/host-catalog.json`; resolution merges Host defaults
with Plugin Root differences and produces the complete immutable App Plan.

The built-root commands in section 2 require an executable Host Build and
`host-catalog.json` generated from that exact build. They define which linked
Plugins, Slots, Execution Adapters, and defaults the product actually supports;
the generic CLI cannot invent them. The source-App commands in section 3
instead build a new Host from the adopted inputs.

## 1. Understand the App files

```text
my-app/
├── .lenso/
│   ├── host
│   └── host-catalog.json
└── plugins/
    └── example.echo/
        ├── plugin.lenso-plugin/
        ├── default.toml
        ├── default/
        │   └── prompt.md
        └── old.disabled
```

- `plugin.lenso-plugin/` is the verified extracted Bundle;
- `<instance>.toml` adds or configures a keyed Instance;
- `<instance>/` contains immutable resources for that configured Instance;
- `<instance>.disabled` is an empty marker that disables an existing Instance.

## 2. Change the App through the CLI

Use the CLI to preserve these invariants:

```sh
lenso app init --host ./host --host-catalog ./host-catalog.json --root ./my-app
lenso plugins add ./example.echo/dist/example.echo-0.1.0.lenso-plugin --root ./my-app
lenso plugins configure example.echo default --file ./echo.toml --root ./my-app
lenso plugins disable example.echo default --root ./my-app
lenso plugins enable example.echo default --root ./my-app
lenso plugins remove example.echo default --root ./my-app
lenso plugins remove example.echo --root ./my-app
lenso app check --root ./my-app
lenso app show --root ./my-app
```

Every mutation first resolves a candidate snapshot against the Host Catalog.
Invalid configuration, missing required Slots, unknown Plugins, and ambiguous
bindings fail before files are committed. The running product Host separately
stages a Generation, passes its Ready Gate, switches routing, drains the old
Generation, and can roll back runtime failure.

Passing an Instance key to `remove` deletes only that App-owned difference.
Omitting it removes the entire Plugin directory through the recoverable
`.lenso/trash/` path.

`plugins list` shows every derived Plugin Instance and its source. `app show`
explains the complete derived App, including Host defaults and Capability
bindings. `app check` is the shortest validation after a manual review or
merge.

## 3. Choose the release path by distribution

The older published Portable Bundle workflow uses `lenso plugins` commands
like these. They require a real downloadable Bundle and a compatible Host;
they do **not** adopt a linked Rust `.crate` into a source App:

```sh
lenso plugins search tool
lenso plugins install example.tool --version 1.2.0
lenso plugins update example.tool --version 1.3.0
lenso plugins history example.tool
lenso plugins rollback example.tool --version 1.2.0
```

There is no implicit “latest.” Catalog and Bundle schemas are strict, network
downloads are digest-bound, and retained versions are immutable. The official
catalog may truthfully be empty until a Release has a real downloadable Bundle.
The `example.tool` coordinates above are illustrative, not a claim of an
available release.

For the exact signed paths below, build the source CLI as in
[Create a local Web App](/docs/core/app-quickstart) and set `LENSO_CLI` to
its absolute binary path. This candidate CLI accepts one exact signed Portable
Release as a source App input. The snapshot, public trust configuration, and matching
`.lenso-plugin` must be supplied independently; a Site listing is not an
installation grant:

```sh
"$LENSO_CLI" plugins signed-search \
  --snapshot /absolute/path/to/signed-portable.json \
  --trust /absolute/path/to/public-trust.json --json
"$LENSO_CLI" app add "$PLUGIN_ID@$VERSION" --root . \
  --portable-snapshot /absolute/path/to/signed-portable.json \
  --trust /absolute/path/to/public-trust.json \
  --archive /absolute/path/to/exact-release.lenso-plugin
"$LENSO_CLI" app build --out dist-portable-review
"$LENSO_CLI" app check --root dist-portable-review/intent
"$LENSO_CLI" app show --root dist-portable-review/intent --json
```

`app add` checks the signed payload, freshness, exact release identity,
archive digest, and manifest before recording the source App intent. A later
build checks the local archive against its lock; it does not establish a new
independent signature authority over an App owner's editable source tree.
Inspect the Host target and permissions, and run an untrusted Bundle only in
an appropriately isolated Host. These coordinates are placeholders, not a
claim that a public Portable release or CLI binary is available.

The same CLI also has a separate exact signed linked Cargo path. In a source
App, first inspect an operator-supplied signed snapshot with its local public
trust configuration. Only after you have the exact matching
registry `.crate` archive and have reviewed its Host target and integration,
the command shape is:

```sh
"$LENSO_CLI" app linked-catalog \
  --linked-snapshot /absolute/path/to/signed-linked.json \
  --trust /absolute/path/to/public-trust.json --json
"$LENSO_CLI" app add "$PLUGIN_ID@$VERSION" --root . \
  --linked-snapshot /absolute/path/to/signed-linked.json \
  --trust /absolute/path/to/public-trust.json \
  --crate /absolute/path/to/exact-package.crate
"$LENSO_CLI" app build --out dist-linked-review
"$LENSO_CLI" app check --root dist-linked-review
"$LENSO_CLI" app show --root dist-linked-review --json
```

`PLUGIN_ID`, `VERSION`, and the file paths above are placeholders, not a
published release. `app add` checks the signature, exact identity/version,
crate digest, and Native Host target before adopting source. This Site's
unsigned candidate documentation is not one of those inputs. A signed
listing without its `.crate` and trust material is still not an installation
result; a successful adoption still needs the build, check, and real App call.

The Kernel never reads this directory and never installs a package. It receives
only the resolved Plan selected for one App Generation.
