---
title: Auth Plugin
description: Use the wire-neutral Auth Capability for API tokens, or compose the supported browser OIDC session flow.
---

Lenso Auth has two layers that must stay separate:

1. `lenso.auth@1` accepts protocol-neutral credential evidence and returns a
   short-lived, signed `ActorAssertion`.
2. Ingress and provider Plugins adapt a wire protocol such as Bearer or
   browser OIDC into that Capability.

The target Plugin still performs the final authorization check. It verifies the
assertion's issuer, Ed25519 proof, exact audience, and validity before it uses
the subject or claims.

```text
Ingress Adapter -> CredentialEvidence -> Auth Provider
               <- absent | signed ActorAssertion | Domain Error
Target Plugin  <- verified, audience-limited assertion
```

## What is available now

| Path | Current source behavior | Ownership boundary |
| --- | --- | --- |
| API-token Auth | PostgreSQL-backed opaque token/session provider; explicit setup, issue, and revoke operations | Provider owns token digest and revocation; target Plugin owns authorization |
| Browser OIDC session | External OIDC Client + Auth Web Session Adapter + Web Ingress Cookie/CSRF policy | OIDC provider validates identity; Web Session emits responses and Cookies; Ingress selects credentials and enforces CSRF |
| Portable `lenso.auth@1` | One `authenticate` operation over protocol-neutral evidence | No Cookie, header, OAuth, or password semantics enter the Capability |
| Generic OAuth/password/cookie providers, Organization/RBAC policy, and Console UI | Deferred from this framework workflow | Add an explicit Provider or owning product surface; do not put it in the Kernel |

The browser row is a composition of the external relying-party Plugin
(`lenso-auth-oidc-client-plugin`) and the removable HTTP Adapter
(`lenso-auth-web-session-plugin`). It is different from
`lenso-auth-oidc-plugin`, which makes a Lenso App an OIDC issuer.

## Browser OIDC login

Compose one Federated provider, Auth Web Session, and Web Ingress on the same
Ingress origin. The provider's registered redirect URI must resolve to the
fixed `/auth/oidc/callback` route. The Federated provider and Web Session must
bind the same App session issuer so that the Adapter can revoke the credential
it receives.

### Configure the browser boundary

Auth Web Session accepts two configuration fields:

```text
session_cookie_name = "__Host-lenso-session"
csrf_cookie_name    = "__Host-lenso-csrf"
```

Both names must be valid, distinct `__Host-` Cookie names. Configure Web
Ingress with the same two names and one dedicated CSRF request-header name.
The source validates these names when the Plugin is prepared; it does not
accept a shared name or a Cookie name with a `Domain` attribute.

The Web Session Plugin has no session database. Account Auth owns opaque
session credentials and revocation. Web Session owns route responses and
Cookie issuance. Web Ingress owns Cookie parsing, credential selection, the
Authorization/Cookie ambiguity check, and double-submit CSRF enforcement before
the Endpoint runs.

### Follow the login flow

1. Start from an App-local path:

   ```sh
   curl -i 'http://127.0.0.1:8788/auth/oidc/start?return_to=%2Fdashboard'
   ```

   `GET /auth/oidc/start` validates `return_to` as an App-local absolute path
   and returns `302` to the configured identity provider. The Federated provider
   creates the single-use flow and performs the authorization-code exchange
   with PKCE. Do not use an external URL as `return_to`.

2. Let the identity provider return the browser to:

   ```text
   GET /auth/oidc/callback?code=<authorization-code>&state=<single-use-state>
   ```

   The callback rejects missing, invalid, expired, or replayed values. The
   bound OIDC Client validates the issuer, client audience, JWKS signature,
   expiry, issued-at time, and nonce before it obtains the canonical subject
   and opaque session from the bound Directory and Credential Issuer.

   On success the Adapter returns `303`, sets an opaque session Cookie with
   `Secure`, `HttpOnly`, `SameSite=Lax`, and `Path=/`, sets a separate readable
   CSRF Cookie with `Secure`, `SameSite=Lax`, and `Path=/`, then redirects only
   to the validated local path.

3. For every unsafe request authenticated by the session Cookie, browser code
   copies the readable CSRF Cookie into the configured Ingress CSRF header:

   ```sh
   curl -i -b cookies.txt \
     -H '<configured-csrf-header>: <csrf-cookie-value>' \
     -X POST 'http://127.0.0.1:8788/example'
   ```

   Web Ingress compares the two values before dispatch. It strips the Cookie
   and CSRF header before the target Endpoint receives the protocol-neutral
   selected credential.

4. Log out with the selected session:

   ```sh
   curl -i -b cookies.txt \
     -H '<configured-csrf-header>: <csrf-cookie-value>' \
     -X POST 'http://127.0.0.1:8788/auth/logout'
   ```

   `POST /auth/logout` accepts only the selected `session` credential, asks the
   bound Credential Issuer to revoke that exact opaque value, and expires both
   Cookies. An absent credential is cleared with `204`; an unrecognized
   credential is cleared but returns `401` so the Adapter never claims a
   revocation it could not confirm.

## API-token evidence and target authorization

An HTTP Adapter can select one Bearer credential and pass only protocol-neutral
evidence into the Auth Capability:

```rust
use lenso_auth_sdk::{
    AuthOutcome, CredentialEvidence, authenticate_request, decode_auth_response,
};
use lenso_capability_auth::{Auth, AUTHENTICATE_OPERATION};

let response = app
    .invoke::<Auth>(
        "api-ingress",
        AUTHENTICATE_OPERATION,
        authenticate_request(Some(CredentialEvidence::new("bearer", token))),
    )
    .await??;

match decode_auth_response(response)? {
    AuthOutcome::Absent => { /* continue anonymously or reject */ }
    AuthOutcome::Authenticated(assertion) => {
        let context = assertion.attach(app.invocation_context(None, cancellation))?;
        // The target verifies and projects this assertion for its own operation.
        let _ = context;
    }
}
```

The API Token Plugin stores a keyed digest, checks durable token/session
revocation on every authentication, and issues a short-lived Ed25519 assertion.
Database setup, token issuance, and revocation are explicit operator work; App
boot does not create or migrate the schema. The current source crate is kept
private while its pinned dependencies are released.

For target-side authorization, the expected audience is exact, for example
`orders.api@1:read`. A target receives the public verification key and never
the Auth signing key. Typed actor projection belongs to the target Plugin.

## Troubleshoot and verify

| Symptom | Check |
| --- | --- |
| `400 invalid_return_to` | Use an App-local absolute path such as `/dashboard`; never pass an external URL. |
| `400 invalid_oidc_callback` | Confirm both `code` and `state` are present, within the route limits, and that the state was not already consumed. |
| `401 oidc_authentication_rejected` | Inspect the bound OIDC provider's issuer, audience, JWKS, expiry, issued-at, and nonce validation. |
| Cookies are absent after callback | Check the redirect URI, HTTPS/secure-cookie context, and that both Plugins use distinct `__Host-` names. |
| Unsafe request is rejected before the Endpoint | Copy the readable CSRF Cookie into the exact Ingress-configured header; the names and values must match. |
| Logout returns `401` | The selected credential is not recognized by the bound issuer; Cookies are still cleared. |
| Login start is unavailable | Check the Federated provider and its egress dependency. The Adapter returns `503` for provider unavailability. |

Use the real Web Ingress in verification. A successful start should produce
`302`; a successful callback should produce `303` and two `Set-Cookie` headers;
an unsafe Cookie-authenticated request without matching CSRF evidence should be
rejected before the Endpoint; and logout should revoke the selected credential
and clear both Cookies.
