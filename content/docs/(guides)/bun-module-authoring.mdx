---
title: Bun Module authoring
description: Scaffold, implement, and run a typed Bun Module through the production Execution Adapter.
---

Bun is an official Module execution path. A Bun Module implements generated
Capability Provider interfaces; it does not implement a second runtime graph or
the Adapter wire. The Rust Host uses the `lenso.bun-process@1` Execution
Adapter for process startup, handshake, bounded JSON-RPC, deadlines,
cancellation, shutdown, and host-failure translation.

## Prerequisites

- Bun 1.2.21 or newer
- the published Lenso CLI, installed from npm or crates.io

```sh
npm install -g @lenso/cli
# or: cargo install lenso-cli --locked
lenso --version
bun --version
```

The npm CLI contains the platform binary and publishes provenance.
`@lenso/bun-module` owns Module serving, while `@lenso/bun` publishes the
official Lenso Capability projections that Bun Modules can import directly.

## Create a complete Bun project

Create the Capability contract, generated TypeScript binding, typed
Provider, App Composition, and Bun workspace with one command:

```sh
lenso module create greeting --runtime bun
cd greeting
lenso module dev
```

By default, creation stages the entire project, runs `bun install` and the
TypeScript check, then publishes the new directory atomically. An existing
target is never overwritten. Use `--no-install` for an offline scaffold,
`--dir PATH` for a different target, or
`--capability example.greeting@1` for an explicit Capability identity.

The generated project is self-contained:

```text
greeting/
├── contracts/greeting/
│   ├── capability.json
│   ├── generated/
│   │   └── bindings.ts
│   └── schemas/
├── modules/greeting/
│   ├── package.json
│   └── src/index.ts
├── bun.lock
├── lenso.json
├── package.json
└── tsconfig.json
```

`lenso.json` selects the workspace package, its script entrypoint, the
`lenso.bun-process@1` execution class, and the exact generated endpoint. The
ordinary `bun.lock` remains the package-resolution authority.

## Implement the generated Provider

The scaffold starts with a typed Request Provider:

```ts title="modules/greeting/src/index.ts"
import { defineModule, serve } from "@lenso/bun-module";
import {
  bindProvider,
  type Provider,
} from "../../../contracts/greeting/generated/bindings.ts";

const provider: Provider = {
  async execute(_context, request) {
    if (request.input.trim().length === 0) {
      return {
        ok: false,
        error: { kind: "domain", error: "invalid_input" },
      };
    }

    return {
      ok: true,
      value: { output: `Hello from Bun, ${request.input}!` },
    };
  },
};

serve(defineModule({ providers: [bindProvider(provider)] }));
```

Generated bindings own the request, response, Domain Error, context, and
Provider types. `@lenso/bun-module` owns the Module-side handshake and server;
business code should not parse `--lenso-*` flags, JSON-RPC envelopes, sessions,
or process signals.

Return generated Domain Errors for expected business outcomes. Thrown errors
remain operational failures and are mapped truthfully at the Adapter boundary.

## Develop with a fresh Plan

Run the development loop from the project root:

```sh
lenso module dev
# equivalent workspace script
bun run dev
```

The command checks the contract and package lock, resolves a fresh immutable
App Plan, and starts the production JSON-RPC Bun Adapter. A relevant source,
Descriptor, schema, manifest, lockfile, or `lenso.json` change cleanly stops the
current child, resolves again, and starts a fresh generation. A type, contract,
or startup failure keeps the watcher alive so the next edit can recover it.
Ctrl-C performs cooperative shutdown.

Use an alternate executable or project document only when needed:

```sh
lenso module dev --bun-bin /opt/bun/bin/bun
lenso module dev --project path/to/lenso.json
```

## Check and resolve

The scaffold provides the repeatable CI commands:

```sh
bun run typecheck
bun run check
bun run resolve
lenso module verify
```

`check` validates the Descriptor, checked-in generated bindings, package lock,
entrypoint, endpoint, and execution class. `resolve` writes the canonical Plan;
the running Kernel does not install packages, discover Providers, or mutate
that graph.

## Supported interaction surface

`@lenso/bun-module` 0.1 supports typed Request Providers over the production
JSON-RPC loopback wire. It rejects Stream or Event descriptors at startup
rather than exposing a partial authoring contract. The lower-level Bun Adapter
already has cross-runtime Stream and Event conformance, but those interactions
are not a public high-level Bun Module authoring surface yet.

See the
[`@lenso/bun-module` package](https://www.npmjs.com/package/@lenso/bun-module)
for the Module API and
[`lenso-bun-adapter`](https://github.com/LioRael/lenso-bun-adapter)
for the Execution Adapter and real cross-runtime evidence.
