title: Write the Endpoint Plugin
description: Create one linked Rust Plugin with typed JSON routes and prove its behavior before opening a socket.
---

This step produces `company.greetings-http`, a Plugin that provides two
`lenso.http.endpoint@1` routes. Complete it before touching Ingress.

| Operation | HTTP method | Path |
| --- | --- | --- |
| `greetings.create` | `POST` | `/greetings` |
| `greetings.search` | `QUERY` | `/greetings/search` |

## 1. Generate the Plugin

Install the CLI from the [Plugin quickstart](/docs/core/quickstart), then use
its Web authoring path. The layout below is generated by native CLI `0.6.4`
from npm `@lenso/cli@0.17.4`:

```sh
lenso plugin new company.greetings-http --web
cd company.greetings-http
```

The command creates a standalone linked Rust Plugin:

```text
company.greetings-http/
├── Cargo.toml
├── build.rs
├── README.md
└── src/
    ├── lib.rs
    └── routes/
        ├── create.rs
        └── search.rs
```

Its manifest already declares the Web root slot and pins compatible framework
revisions:

```toml title="Cargo.toml"
[package.metadata.lenso]
plugin-id = "company.greetings-http"
root-slot = "web"
```

By default, generation also creates `Cargo.lock` and runs the socket-free test.
Use `--no-install` only when dependency resolution must happen later. When you
move the crate into a Host workspace, replace the pinned dependencies with that
workspace's dependency entries and remove the scaffold's standalone
`[workspace]` table. If you copy or rename the scaffold, or change its manifest,
regenerate the affected `Cargo.lock` with `cargo generate-lockfile` from the
crate or workspace root before `cargo test --locked` or `lenso app build`. A
stale lockfile fails the build's locked Cargo metadata check.

## 2. Implement the routes

Keep the generated `src/lib.rs`, `build.rs`, and `src/routes/create.rs`.
Keep create's `#[post("greetings.create", "/greetings")]` attribute unchanged.
`src/lib.rs` owns the shared request/response types and `GreetingsHttp` state.
Each file under `src/routes/` contains one handler; the build script combines
those handlers into the `#[endpoint]` implementation included by `src/lib.rs`.
Do not add a second inline implementation or remove that generated include.

The scaffold initially uses **POST** for both routes. This tutorial deliberately
changes search to **QUERY**. In `src/routes/search.rs`, change only the first
attribute as shown, retaining the handler and its other attributes:

```diff title="src/routes/search.rs"
-#[post("greetings.search", "/greetings/search")]
+#[query("greetings.search", "/greetings/search")]
```

The generated create handler stores a greeting and returns `201`; the search
handler returns matching greetings. Both reject empty input with a `400`
Problem. The existing tests select the operation IDs, so they remain valid
when this search method changes. Rebuild before using the QUERY requests in
[Prove the HTTP backend](/docs/web/web-testing).

`#[lenso::plugin]` declares the product behavior boundary. `#[endpoint]`
generates the route description, dispatch path, `lenso.http.endpoint@1`
Capability, and linked Plugin factory from the same declarations. Product code
does not implement `NativePluginFactory`, and must not use the retired
`NativeModuleFactory` API. The Plugin must be a named-field struct. If it has
no state, declare `pub struct PreviewHttp {}` rather than the unit struct
`pub struct PreviewHttp;`; the Plugin macro rejects unit structs. A handler
returns business-facing values:
`Json<T>` means a `200` JSON response, `(StatusCode, T)` overrides its status,
and `Problem` is an intentional client-visible failure. The macro lowers these
values into the portable Capability contract. Use
`Result<Json<T>, Problem>` as the handler return type, including for a list
operation. For a bodyless delete response, return `Result<HandleResponse, Problem>`
with `Ok(lenso_capability_http_endpoint::response::empty(StatusCode::NO_CONTENT))`.

`Json<T>` also rejects malformed JSON and unsupported content types before the
handler runs. `Path<T>` decodes named path parameters, while `QueryParams<T>`
decodes URL query strings. Use `#[query("route.id", "/path")]` for the HTTP
QUERY method—a safe, idempotent request that may carry a structured body. It is
not the same thing as URL query parameters.

The map is temporary Instance state. Move shared business facts into a business
Capability provider when another interface also needs Greeting behavior. Put
durable state in a selected Store Plugin, not in Ingress.

## 3. Prove the provider directly

The scaffold already has a socket-free `tests` module in `src/lib.rs`. Add
this function inside that existing module; keep its imports and generated
negative-path tests:

```rust title="src/lib.rs — inside mod tests"
#[test]
fn finds_the_created_greeting() {
    block_on(async {
        let endpoint = EndpointTest::new(GreetingsHttp::default());
        let created = endpoint
            .request("greetings.create")
            .json(&CreateGreeting {
                name: "Lenso".to_owned(),
            })
            .unwrap()
            .send()
            .await
            .unwrap();
        assert_eq!(created.status(), StatusCode::CREATED);
        let found = endpoint
            .request("greetings.search")
            .json(&SearchGreetings {
                term: "Lenso".to_owned(),
            })
            .unwrap()
            .send()
            .await
            .unwrap();
        assert_eq!(found.json::<Vec<Greeting>>().unwrap().len(), 1);
    });
}
```

`EndpointTest` reads method and path from the generated route table. It invokes
the Plugin directly, so it tests extractors, middleware, typed responses, and
dispatch without binding a port. Its request builder also supports `.query()`,
`.path_parameter()`, and `.header()`.

Add focused tests against the generated `EndpointProvider`:

- `describe` returns exactly `greetings.create` and `greetings.search`;
- valid JSON returns `201`;
- empty `name` returns an intentional `400` Problem Details response;
- malformed JSON and unsupported content types fail before `create` runs; and
- `greetings.search` uses the HTTP QUERY method and accepts a JSON body.

Run the crate's checks:

```sh
cargo fmt --all
cargo fmt --all -- --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
```

The owner repository also has a complete inline Endpoint example at
`examples/greetings-http-plugin`; its layout is separate from the generated
route-file scaffold above. It maintains extractor and response examples:

```sh
cargo test --locked -p lenso-capability-http-endpoint \
  --test endpoint_attributes
```

This step is complete when the `POST /greetings` and `QUERY /greetings/search`
route descriptions are stable and every direct success and failure assertion
passes. Continue with
[Connect the Host and Ingress](/docs/web/web-host-integration).
