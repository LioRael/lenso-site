---
title: 配置 Agent
description: 在本地配置 Plugin Resource，或使用当前的单 Resource Agent 配置服务。
---

Agent 运行一个本地 Plugin Root。当前的远程配置切片是一个明确的小型服务：它只服务
一个 `app`/`environment` Resource，并由一个持久 Root 与 SQLite Authority 支持。它是
配置与发布边界，不是多 Resource Hosted Control Plane。

## 可用性与所有权

| Surface | 当前行为 | 所有者 |
| --- | --- | --- |
| Local Agent Home | `~/.lenso/agent` 包含 Host Catalog、受管理的 `plugins/` Root 与 Profile | 本地 Host 及其 Plugin Root |
| Managed local control | Agent Web 可以使用 `--plugin-control` 与可选的绝对 SQLite Store，保存 Proposal、Publication History 与 Rollback Proposal | 嵌入式 Host；SQLite 是单 Host 状态 |
| Configuration service | `lenso-plugin-configuration-service` 只服务一个已配置的 App/environment Resource 及其 Plugin 配置 Route | Agent Web 服务及其专用 Root 与 SQLite 数据库 |
| Multi-resource Hosted Control Plane、通用 Administration API、Tenancy 与远程编写的 Plan | Deferred | 需要明确的产品与所有权决策 |

Configuration Service 持有 Desired Plugin Configuration、Revision Fence、Proposal Digest 与
Publication Evidence。配置中的 Plugin 持有自己的 Schema 与业务行为。Host 解析并激活它实际
运行的 App Plan 与 Generation。Console 可以作为这些 Route 的 Client，但不会成为 Plugin
业务数据或授权的所有者。

## 1. 配置本地 Agent Home

默认 Agent Home 是 `~/.lenso/agent`：

```text
~/.lenso/agent/
├── .lenso/host-catalog.json
├── plugins/
│   └── lenso.agent.loop/
│       └── agent.toml
└── profiles/
    └── code.toml
```

创建 Plugin Instance Patch 并检查它：

```toml title="agent-loop.toml"
model = "gpt-5.6-luna"
max_steps = 9
max_tool_calls = 4
max_user_resumes = 8
max_parallel_tool_calls = 4
max_output_tokens = 1024
max_history_events = 200
max_compaction_summary_characters = 8192
max_memory_items = 8
max_memory_characters = 16384
```

```sh
lenso plugins configure lenso.agent.loop agent \
  --file ./agent-loop.toml \
  --root "$HOME/.lenso/agent"
lenso plugins list --root "$HOME/.lenso/agent"
lenso app show --root "$HOME/.lenso/agent"
lenso app check --root "$HOME/.lenso/agent"
```

Package Default、Host Configuration 与 Instance Patch 合并后才会校验最终 Schema。未知
字段或无效值会在可见 Plugin Root 改变前失败。Secret 值放在选中的 Secret Provider 中；
TOML 只保存 Reference 或映射。

## 2. 启动单 Resource Configuration Service

为服务准备一个专用 Root，并放入兼容 Host Build 的准确 Host Catalog。Root 必须是绝对的
UTF-8 路径，包含 `.lenso/host-catalog.json` 与受管理的 `plugins/` 物化结果。不要把它
与正在运行的 Host 共用。

从 Agent 源码 Checkout 启动服务：

```sh
LENSO_PLUGIN_CONFIGURATION_SERVICE_READ_TOKEN=<read-token> \
LENSO_PLUGIN_CONFIGURATION_SERVICE_WRITE_TOKEN=<write-token> \
  cargo run -p lenso-agent-web \
  --no-default-features \
  --bin lenso-plugin-configuration-service -- \
  --listen 127.0.0.1:8790 \
  --root /var/lib/lenso-config/agent-production \
  --database /var/lib/lenso-config/agent-production/configuration.sqlite3 \
  --app agent \
  --environment production
```

服务会校验绝对 Root，在绑定前读取 Host Catalog，并把唯一 Resource 标识为
`agent/production`。Database Path 也必须是绝对路径，用于保存 CAS、Proposal 与
Publication Evidence。

两个服务 Credential 必须分开且不能相同：

| Credential | 允许的操作 |
| --- | --- |
| `LENSO_PLUGIN_CONFIGURATION_SERVICE_READ_TOKEN` | 检查当前 Revision、读取 Publication History、观察有界 Change Feed |
| `LENSO_PLUGIN_CONFIGURATION_SERVICE_WRITE_TOKEN` | 构建 Proposal、发布审查后的 Configuration、创建 Rollback Proposal；也允许读取 |

不要把 Token 放入命令行参数或源码。非 Loopback 部署应在前面配置 TLS；Credential 与 TLS
Secret 的分发属于部署责任。

## 3. 寻址单个 Resource

服务 URL 以配置的 Resource 为根：

```sh
BASE='http://127.0.0.1:8790/v1/apps/agent/environments/production'
export LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN=<service-token>

curl -sS \
  -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
  "$BASE/plugins" | jq '{revision, schema}'
```

Path 必须匹配服务配置的 App 与 Environment。其他身份返回 `404`；缺失或无效的 Bearer
Token 返回 `401`。服务在这个 Resource 下提供 Plugin Configuration Route，例如：

```text
GET  /v1/apps/{app}/environments/{environment}/plugins
GET  /v1/apps/{app}/environments/{environment}/changes
POST /v1/apps/{app}/environments/{environment}/plugins/{plugin}/{instance}/configuration/proposals
PUT  /v1/apps/{app}/environments/{environment}/plugins/{plugin}/{instance}/configuration
GET  /v1/apps/{app}/environments/{environment}/plugins/{plugin}/{instance}/configuration/publications
POST /v1/apps/{app}/environments/{environment}/plugins/{plugin}/{instance}/configuration/rollback-proposals
```

这是一个 Resource 下的多个 Plugin/Instance Record，不是通用 Resource Registry，也不是
编辑 App Plan 的 API。

## 4. 提议、审查与发布

先读取当前 Semantic Revision，再使用该 Revision 提交确切的 TOML 字节：

```sh
REVISION=$(curl -sS \
  -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
  "$BASE/plugins" | jq -r '.revision')
CONFIG_TOML=$(<agent-loop.toml)

PROPOSAL=$(jq -n \
  --arg expectedRevision "$REVISION" \
  --arg toml "$CONFIG_TOML" \
  '{expectedRevision: $expectedRevision, toml: $toml}' | \
  curl -sS -X POST \
    -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
    -H 'Content-Type: application/json' \
    --data-binary @- \
    "$BASE/plugins/lenso.agent.loop/agent/configuration/proposals")

printf '%s' "$PROPOSAL" | jq '{status, application, baseRevision, candidateRevision, proposalDigest, diagnostics}'
```

Proposal 是只读的。`status` 可以是 `ready`、`needs_decision` 或 `rejected`；`application`
可以是 `noop`、`app_generation` 或 `blocked`。诊断要求决策或状态为 rejected 时，不能发布。

使用相同的 Expected Revision 发布完全相同的 TOML 与 Digest：

```sh
PROPOSAL_DIGEST=$(printf '%s' "$PROPOSAL" | jq -r '.proposalDigest')
jq -n \
  --arg expectedRevision "$REVISION" \
  --arg proposalDigest "$PROPOSAL_DIGEST" \
  --arg toml "$CONFIG_TOML" \
  '{expectedRevision: $expectedRevision, proposalDigest: $proposalDigest, toml: $toml}' | \
  curl -sS -X PUT \
    -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
    -H 'Content-Type: application/json' \
    --data-binary @- \
    "$BASE/plugins/lenso.agent.loop/agent/configuration" | \
  jq '{status, baseRevision, proposalDigest, revision}'
```

接受发布会返回 `status: "published"` 与新的 Revision。使用旧 Revision、改变 TOML Body
或使用不同 Digest 的 Writer 会被拒绝并返回 Conflict。应读取最新 Revision、重新构建
Proposal 并再次审查；不要覆盖当前 Root。

服务会保存 Publication History。Rollback 首先从旧 Digest 创建一个新的受 Revision Fence
保护的 Proposal，而不是回退数据库：

```sh
curl -sS \
  -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
  "$BASE/plugins/lenso.agent.loop/agent/configuration/publications" | jq '.publications'
```

使用返回的 `proposalDigest` 调用 `rollback-proposals` Route，审查 `configurationToml` 与
嵌套 Proposal，再通过相同的 `PUT` Route 发布完全相同的字节。

## 5. 观察 Reconciliation 与故障

Publication 会改变 Desired State 并写入 Evidence。随后 Host 物化受管理的 Plugin Root，
根据不可变 Host Catalog 解析它，暂存 Candidate Generation，并只在 Readiness 通过后切换。
通过 Host 的 Agent Surface 分别观察 Desired 与 Applied State。

远程 Configuration 采用 Fail-closed。服务故障会使检查、Proposal、Publication 或 Change
Watching 失败；Adapter 不会悄悄回退到本地 Root。Change History 缺失或顺序错误也会 Fail-closed；
没有完整 Root 覆盖的回退路径。恢复服务或修复 Revision Chain 后，从最后一个已验证的
Revision 重试。

## Deferred 行为

当前源码没有建立多 App 或多 Environment Registry、Hosted Tenancy、通用 Administration API、
Console-owned Authorization Model 或远程编写的 App Plan。不要把它们写成部署承诺。当前支持的
边界是一个命名 Resource、两个作用域分离的 Bearer Credential、受 Revision Fence 保护的
Plugin Configuration，以及 Host-local Plan 与 Generation 激活。
