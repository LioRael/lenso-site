---
title: Configure an Agent
description: Configure Plugin resources locally or through the current single-resource Agent configuration service.
---

An Agent runs a local Plugin Root. The current remote configuration slice is a
small, explicit service for one `app`/`environment` resource backed by one
durable root and SQLite authority. It is a configuration and publication
boundary; it is not a hosted multi-resource control plane.

## Availability and ownership

| Surface | Current behavior | Owner |
| --- | --- | --- |
| Local Agent Home | `~/.lenso/agent` contains the Host Catalog, managed `plugins/` root, and Profiles | The local Host and its Plugin Root |
| Managed local control | Agent Web can use `--plugin-control` and an optional absolute SQLite store for proposals, publication history, and rollback proposals | The embedding Host; SQLite is single-Host state |
| Configuration service | `lenso-plugin-configuration-service` serves exactly one configured App/environment resource and its Plugin configuration routes | Agent Web service plus its dedicated root and SQLite database |
| Multi-resource hosted control plane, general administration API, tenancy, and remote-authored Plans | Deferred | Requires an explicit product and ownership decision |

The configuration service owns desired Plugin configuration, revision fencing,
proposal digests, and publication evidence. The configured Plugin owns its
schema and business behavior. The Host resolves and activates the App Plan and
Generation it actually runs. Console may be a client of these routes, but it
does not become the owner of Plugin business data or authorization.

## 1. Configure a local Agent Home

The default Agent Home is `~/.lenso/agent`:

```text
~/.lenso/agent/
├── .lenso/host-catalog.json
├── plugins/
│   └── lenso.agent.loop/
│       └── agent.toml
└── profiles/
    └── code.toml
```

Create a Plugin Instance patch and inspect it:

```toml title="agent-loop.toml"
model = "gpt-5.6-luna"
max_steps = 9
max_tool_calls = 4
max_user_resumes = 8
max_parallel_tool_calls = 4
max_output_tokens = 1024
max_history_events = 200
max_compaction_summary_characters = 8192
max_memory_items = 8
max_memory_characters = 16384
```

```sh
lenso plugins configure lenso.agent.loop agent \
  --file ./agent-loop.toml \
  --root "$HOME/.lenso/agent"
lenso plugins list --root "$HOME/.lenso/agent"
lenso app show --root "$HOME/.lenso/agent"
lenso app check --root "$HOME/.lenso/agent"
```

The final schema is checked after package defaults, Host configuration, and the
Instance patch are merged. An unknown field or invalid value fails before the
visible Plugin Root changes. Keep secret values in a selected Secret Provider;
TOML should contain only references or mappings.

## 2. Start the single-resource configuration service

Prepare a dedicated service root with the exact Host Catalog from a compatible
Host build. The root must be an absolute UTF-8 path containing
`.lenso/host-catalog.json` and the managed `plugins/` materialization. Do not
share this root with a running Host.

Start the service from an Agent source checkout:

```sh
LENSO_PLUGIN_CONFIGURATION_SERVICE_READ_TOKEN=<read-token> \
LENSO_PLUGIN_CONFIGURATION_SERVICE_WRITE_TOKEN=<write-token> \
  cargo run -p lenso-agent-web \
  --no-default-features \
  --bin lenso-plugin-configuration-service -- \
  --listen 127.0.0.1:8790 \
  --root /var/lib/lenso-config/agent-production \
  --database /var/lib/lenso-config/agent-production/configuration.sqlite3 \
  --app agent \
  --environment production
```

The service validates the absolute root, reads the Host Catalog before binding,
and identifies exactly one resource as `agent/production`. The database path is
also absolute and stores CAS, proposal, and publication evidence.

The two service credentials are separate and must be distinct:

| Credential | Permitted operations |
| --- | --- |
| `LENSO_PLUGIN_CONFIGURATION_SERVICE_READ_TOKEN` | Inspect the current revision, read publication history, and watch the bounded change feed |
| `LENSO_PLUGIN_CONFIGURATION_SERVICE_WRITE_TOKEN` | Build proposals, publish reviewed configuration, and create rollback proposals; it also permits read operations |

Keep tokens out of command-line arguments and source files. Put TLS in front of
non-loopback deployments; credential and TLS secret distribution remain
deployment responsibilities.

## 3. Address the one resource

The service URL is rooted at the configured resource:

```sh
BASE='http://127.0.0.1:8790/v1/apps/agent/environments/production'
export LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN=<service-token>

curl -sS \
  -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
  "$BASE/plugins" | jq '{revision, schema}'
```

The path must match the service's configured App and environment. Another
identity returns `404`; a missing or invalid bearer token returns `401`. The
service exposes Plugin configuration below that one resource, for example:

```text
GET  /v1/apps/{app}/environments/{environment}/plugins
GET  /v1/apps/{app}/environments/{environment}/changes
POST /v1/apps/{app}/environments/{environment}/plugins/{plugin}/{instance}/configuration/proposals
PUT  /v1/apps/{app}/environments/{environment}/plugins/{plugin}/{instance}/configuration
GET  /v1/apps/{app}/environments/{environment}/plugins/{plugin}/{instance}/configuration/publications
POST /v1/apps/{app}/environments/{environment}/plugins/{plugin}/{instance}/configuration/rollback-proposals
```

This is one resource with many Plugin/Instance records. It is not a general
resource registry or an API for editing App Plans.

## 4. Propose, review, and publish

Read the current semantic revision first, then submit the exact TOML bytes with
that revision:

```sh
REVISION=$(curl -sS \
  -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
  "$BASE/plugins" | jq -r '.revision')
CONFIG_TOML=$(<agent-loop.toml)

PROPOSAL=$(jq -n \
  --arg expectedRevision "$REVISION" \
  --arg toml "$CONFIG_TOML" \
  '{expectedRevision: $expectedRevision, toml: $toml}' | \
  curl -sS -X POST \
    -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
    -H 'Content-Type: application/json' \
    --data-binary @- \
    "$BASE/plugins/lenso.agent.loop/agent/configuration/proposals")

printf '%s' "$PROPOSAL" | jq '{status, application, baseRevision, candidateRevision, proposalDigest, diagnostics}'
```

A proposal is read-only. `status` is `ready`, `needs_decision`, or `rejected`;
`application` is `noop`, `app_generation`, or `blocked`. Never publish a
proposal whose diagnostics require a decision or whose status is rejected.

Publish the exact reviewed TOML and digest with the same expected revision:

```sh
PROPOSAL_DIGEST=$(printf '%s' "$PROPOSAL" | jq -r '.proposalDigest')
jq -n \
  --arg expectedRevision "$REVISION" \
  --arg proposalDigest "$PROPOSAL_DIGEST" \
  --arg toml "$CONFIG_TOML" \
  '{expectedRevision: $expectedRevision, proposalDigest: $proposalDigest, toml: $toml}' | \
  curl -sS -X PUT \
    -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
    -H 'Content-Type: application/json' \
    --data-binary @- \
    "$BASE/plugins/lenso.agent.loop/agent/configuration" | \
  jq '{status, baseRevision, proposalDigest, revision}'
```

An accepted publication returns `status: "published"` and a new revision. A
writer that uses an old revision, a changed TOML body, or a different digest is
rejected with a conflict. Fetch the latest revision, rebuild the proposal, and
review it again; do not overwrite the current root.

The service records publication history. A rollback first creates a new
revision-fenced proposal from a prior digest; it is not a database rewind:

```sh
curl -sS \
  -H "Authorization: Bearer $LENSO_PLUGIN_CONFIGURATION_REMOTE_TOKEN" \
  "$BASE/plugins/lenso.agent.loop/agent/configuration/publications" | jq '.publications'
```

Use the returned `proposalDigest` with the
`rollback-proposals` route, review `configurationToml` and the nested proposal,
then publish the exact bytes through the same `PUT` route.

## 5. Observe reconciliation and outages

Publication changes desired state and writes evidence. The Host then
materializes the managed Plugin Root, resolves it against the immutable Host
Catalog, stages a candidate Generation, and switches only after readiness.
Observe desired and applied state separately through the Host's Agent surface.

Remote configuration is fail-closed. A service outage fails inspection,
proposal, publication, or change watching; the adapter does not silently fall
back to a local root. Missing or reordered change history also fails closed;
there is no whole-root overwrite fallback. Restore the service or repair the
revision chain, then retry from the last verified revision.

## Deferred behavior

The current source does not establish a multi-App or multi-environment registry,
hosted tenancy, general administration API, Console-owned authorization model,
or remote-authored App Plan. Do not document those as deployment promises.
The supported boundary is one named resource, two separately scoped bearer
credentials, revision-fenced Plugin configuration, and Host-local Plan and
Generation activation.
